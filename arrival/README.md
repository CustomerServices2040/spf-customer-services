# تحديث 19 نوفمبر 2026: الترحيب داخل المنصة فقط

المسار الحالي: هاتف → تأكيد الوصول → رسالة الترحيب داخل الصفحة. لا يرسل رمز واتساب ولا ينشئ طلب ترحيب خارجي، حتى مع إرسال consent=true. لا تعرض بطاقة البيانات التفصيلية عند البحث بالهاتف؛ تظهر الكنية فقط بعد التسجيل. الهاتف وQR لا يثبتان الهوية أو الوجود المكاني؛ الحالات المحتاجة للتحقق تحال للاستقبال. تظل الاستضافة الخارجية لازمة للتخزين المركزي؛ لم تنشر النسخة ولم يعتمد مزود.

التوثيق أدناه يصف التكامل السابق المحفوظ للمستقبل، وليس المسار الحالي. يجب إبقاء WHATSAPP_ENABLED=false وعدم تشغيل عامل الرسائل.

# الترحيب وتسجيل الوصول — نسخة مراجعة

الحالة: خادم وواجهات منفذة ومختبرة محليا؛ غير منشورين. لا ربط خارجي ولا إرسال واتساب فعلي.

## ما تم تنفيذه

- واجهة عربية RTL مستقلة للمشارك: هاتف عماني، تحقق، مراجعة بيانات، وصول.
- لوحة إدارة محمية بحسابات organizer/reception؛ بحث وتصفية وتعديل وإضافة، تسجيل بواسطة الاستقبال، تصدير XLSX حقيقي.
- تحديث الإدارة كل 3 ثوان، مع تنبيه عند انقطاع التحديث. ليس بثا لحظيا عبر WebSocket.
- SQLite WAL ومعاملات `BEGIN IMMEDIATE`، معرف عشوائي مستقل، قيد فريد للوصول وقيد فريد لرسالة الترحيب لكل مشارك.
- رمز QR موحد متجهي SVG، تحميل وطباعة لوحة استقبال. يستخدم عنوان الخادم المعتمد؛ رمز بيئة المراجعة ليس رمز تشغيل للمدعوين.
- التسجيل مغلق افتراضيا؛ يفتحه المنظم عند الاستقبال ويغلق تلقائيا بعد 12 ساعة. إعادة فتحه تجدد هذه المهلة.
- جلسات HttpOnly وSecure في التشغيل، CSRF، تحقق من Origin، تشفير كلمات المرور scrypt، صلاحيات على الخادم، سجل تدقيق.
- حد للمحاولات على الهاتف وعنوان العميل؛ رموز التحقق 5 دقائق وبحد 5 محاولات، وتذكرة مراجعة 10 دقائق.
- لا تعرض الأسماء أو البيانات قبل رمز تحقق. لا تظهر هوية الرقم غير الموجود؛ تظهر رسالة عدم وجود الرقم المطلوبة، مع تحديد معدل البحث.
- مسار استقبال بديل للمشارك الذي لا يملك رقما أو يتكرر رقمه أو يتعذر عليه واتساب.
- موافقة منفصلة على رسالة التحقق ورسالة الترحيب. لا ينشأ طلب ترحيب عند عدم الموافقة.
- Meta Cloud API الرسمي: قوالب، عامل إرسال منفصل، webhook موقّع. الإرسال معطل افتراضيا.
- فشل الرسالة لا يلغي الوصول. `accepted` لا يعني التسليم. الحالات غير المحسومة لا تعاد آليا لتجنب تكرار الرسالة.

## تحليل الملف المرفق

ورقة «الأسماء»: 38 مدعوا، 37 رقما صالحا بعد توحيد الصيغة، سجل واحد بلا رقم في صف Excel رقم 20، ولا تكرار في أرقام الهاتف. رقم التسلسل الموجود بالملف ليس فريدا. أنشئ لكل مشارك معرف مستقل. استورد الملف في قاعدة خاصة محلية خارج المستودع؛ لا توجد بياناته في GitHub أو النموذج العام.

| المصدر | الاستخدام |
|---|---|
| الاسم | الاسم كما ورد دون تعديل ألقاب |
| اللقب | اسم الترحيب؛ عند غيابه يستخدم الاسم كاملا |
| التقسيم الإداري | عرض وتصفية كما ورد؛ لا يفصل إلى جهة/وظيفة بالافتراض |
| الرقم الهاتف | مفتاح بحث موحد `+968`؛ ليس وسيلة إثبات الهوية وحده |
| اليوم الأول/اليوم الثاني | يحتفظ بهما كما وردا؛ لا يتحولان إلى وصول فعلي |
| تم الرد على المحاور | لا يعرض للمشارك ولا يستخدم لتسجيل الوصول |
| المحافظة | غير موجودة مستقلة؛ تبقى فارغة حتى يضيفها منظم مخول |

وحدة التسجيل الحالية تخص ملتقى واحد وتسجيل وصول واحد للمشارك، ولا تدعي وجود حضور مستقل لكل يوم. إن أريد حضور يومي منفصل فيلزم تحديده قبل التشغيل.

## التشغيل المحلي

من جذر المستودع:

```bash
python -m pip install -r arrival/requirements.txt
python -m arrival.server.manage --db /secure/path/arrival.db import '/private/path/invitees.xlsx'
python -m arrival.server.manage --db /secure/path/arrival.db user organizer --role organizer
python -m arrival.server.manage --db /secure/path/arrival.db user reception --role reception
```

لا توضع قاعدة البيانات أو Excel أو ملفات الأسرار داخل المستودع أو `web/` أو GitHub Pages. مجلد البيانات محمي 0700 والقاعدة 0600. يطلب أمر المستخدم كلمة المرور عبر إدخال مخفي.

لنسخة العرض الاصطناعية فقط:

```bash
python -m arrival.server.manage --db /tmp/busola-review/arrival.db demo
cd arrival
python dev.py --host 127.0.0.1 --port 4173
```

التجربة تستخدم `99000001` ورمز `246810`. الرقم `99000008` مكرر عمدا، و`99000999` غير موجود. حساب العرض الاصطناعي معروف داخل الشفرة، وهو ممنوع على قاعدة المدعوين الحقيقية؛ يرفض الخادم تشغيل وضع demo على قاعدة مستوردة حقيقية.

## إعداد التشغيل بعد الموافقة

يفضل خادم مؤسسي واحد مع قرص دائم مشفر وHTTPS ونسخ احتياطي معتمد. SQLite مناسب لحجم هذا الملتقى ولموظفي استقبال متعددين عبر الخادم نفسه. لا تشغل نسخ خوادم مستقلة بملفات SQLite مختلفة أو على قرص مؤقت. التوسع الأفقي يحتاج تحويل التخزين إلى PostgreSQL؛ هذا التحويل غير منفذ.

متغيرات الخادم، تحفظ في مدير أسرار/بيئة تشغيل خاصة:

- `ARRIVAL_DB`: مسار خاص دائم خارج الشفرة.
- `ARRIVAL_SECRET`: سر عشوائي قوي، 32 محرفا على الأقل. لا تغيّره خلال الملتقى دون تدوير QR والجلسات.
- `PUBLIC_ORIGIN`: عنوان HTTPS النهائي دون مسار أو شرطة ختامية.
- `COOKIE_SECURE=true`, `ARRIVAL_DEMO=false`.
- `WHATSAPP_ENABLED=false` حتى الموافقة على الاختبار الفعلي.
- `META_API_VERSION`: إصدار مدعوم يحدد عند الربط، دون افتراض صلاحية إصدار قديم.
- `META_PHONE_ID`, `META_TOKEN`, `META_APP_SECRET`, `META_VERIFY_TOKEN`.
- `META_AUTH_TEMPLATE`, `META_WELCOME_TEMPLATE`, `META_LANGUAGE=ar`.

```bash
python -m uvicorn arrival.server.run:app --host 127.0.0.1 --port 8000 --proxy-headers --forwarded-allow-ips 127.0.0.1
python -m arrival.server.manage --db /secure/path/arrival.db worker
```

شغل الخادم والعامل كخدمتين يعاد تشغيلهما تلقائيا، مع reverse proxy موثوق وTLS. لا تثق بترويسات forwarded من مصادر غير موثوقة. لا تسجل أجسام الطلبات، أكواد التحقق أو بيانات الدخول في سجلات الشبكة. يعتمد الوقت على ساعة الخادم؛ مزامنتها شرط للتشغيل.

الواجهة والخادم يعملان على الأصل نفسه. وصلة «إدارة تسجيل الوصول» مضافة إلى نسخة الفرع من الملتقى فقط، وتبقى بوابة غير مفعلة حتى ضبط `overrides/forum/arrival/config.js` بعنوان HTTPS المعتمد. لا توضع فيه مفاتيح.

الموافقة على إظهار رابط النظام لا تعني الموافقة على نشر بيانات المدعوين. تصدر QR من الخادم بعد اعتماد عنوانه النهائي؛ QR الموحد وفتح التسجيل لا يثبتان الوجود المكاني بشكل قطعي إذا أعيد توجيه الرابط. يظل فريق الاستقبال مسار التحقق الحضوري.

## إجراءات الربط الحقيقي المتبقية

1. اعتماد الخادم/موقع تخزين البيانات ومدة الاحتفاظ وسجل الحذف، وتوفير HTTPS ونسخ احتياطي واختبار استعادة.
2. تحديد موعد الملتقى وحسابات المنظمين واستكمال الهاتف الناقص عند توفره.
3. تهيئة حساب WhatsApp Business للصندوق ورقم إرسال وصلاحيات Meta والوسيلة المعتمدة للدفع.
4. اعتماد قالب Authentication وقالب الترحيب الوارد في `docs/WHATSAPP_TEMPLATE_AR.txt`، واللغة والنص والتصنيف.
5. إعداد webhook: `/api/meta/webhook`، مع التوقيع وأحداث الرسائل. لم يختبر مع Meta فعليا.
6. الإذن باختبار فعلي على رقم يحدده المستخدم؛ التحقق من تسلم رمز التحقق ثم رسالة الترحيب وعدم التكرار.
7. فحص على هاتف فعلي وشبكة الموقع وشاشة الاستقبال، ثم موافقة نشر مستقلة. لم يختبر مسح QR من هاتف فعلي.

لا يوجد ادعاء exactly-once لدى المزود: عند timeout بعد الإرسال قد يكون المزود قبل الرسالة، فيحفظ النظام الحالة uncertain ويمنع التكرار حتى مراجعتها. لا تعاد إلا حالات failed المؤكدة. العامل لا يعمل تلقائيا في وضع المراجعة.

## التكاليف قبل أي تعاقد

- SQLite والخادم البرمجي: لا رسوم ترخيص. إن توفرت استضافة مؤسسية معتمدة فلا اشتراك قاعدة بيانات خارجي مطلوب؛ تكلفة الاستضافة والتشغيل تعتمد على بيئة الصندوق ولم تسعر هنا.
- البديل المدار Supabase Pro يبدأ من 25 دولارا شهريا وفق صفحة السعر بتاريخ المراجعة 18 نوفمبر 2026، قبل الإضافات. مجرد بديل مقترح؛ لم ينشأ حساب ولم تربط الخدمة، والكود الحالي لا يستخدم Supabase.
- Meta Cloud API المباشر: لا رسوم وصول إضافية للمنصة وفق FAQ، ورسوم الرسائل تعتمد على السوق والفئة والتسليم. القالب النهائي قد يصنف بشكل مختلف؛ لا يعتمد تقدير ثابت قبل موافقة Meta.
- حجم مبدئي: 37 مدعوا ذوي أرقام × (رمز تحقق + ترحيب) = 74 رسالة عند نجاح كل مسار مرة واحدة. تصبح 76 بعد استكمال الرقم الناقص. إعادة طلب الأكواد أو تعدد اليومين قد يزيد العدد.
- احتياطي تخطيطي غير ملزم: 10 دولارات للرسائل لهذه التجربة الصغيرة؛ هذا سقف ميزانية مقترح وليس تسعيرة Meta أو ضمانا للتكلفة. يثبت السعر النهائي من حساب الصندوق قبل تفعيل الإرسال. لا اشتراك أو دفع نفذ.
